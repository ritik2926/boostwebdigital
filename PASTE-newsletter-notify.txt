╔══════════════════════════════════════════════════════════════╗
║ PART 1 — src/lib/newsletter/notify.ts                        ║
╚══════════════════════════════════════════════════════════════╝

export async function notifySubscribers(slug: string):
  Promise<{ sent: number; skipped: string | null }>

Steps, in this exact order:

1. CLAIM THE SLUG FIRST — before fetching anything, before sending anything:

     INSERT INTO sent_posts (post_slug) VALUES ($1)
     ON CONFLICT (post_slug) DO NOTHING
     RETURNING post_slug

   If it returns NO row, this post was already sent. Return immediately with
   { sent: 0, skipped: "already-sent" }.

   ⚠️ This ordering is the whole duplicate guard. WordPress fires its ping
   on every status change, and can fire twice for one publish. Claiming the
   row first means the second ping loses the race and sends nothing. If you
   send first and record after, a double-fire emails the entire list twice.

2. Fetch the post from the WordPress REST API by slug, using the existing
   helpers in src/lib/blog/wordpress.ts. Do not write new fetch code.

3. VERIFY IT IS ACTUALLY PUBLISHED. If the post is missing, or its status is
   not "publish", DELETE the sent_posts row you just claimed and return
   { sent: 0, skipped: "not-published" }.

   Reason: the ping also fires when a post is unpublished or trashed. Without
   this check you would email subscribers about a post that isn't live.

4. Load recipients:
     SELECT email, token FROM subscribers WHERE status = 'confirmed'

   Zero recipients → update recipient_count to 0 and return
   { sent: 0, skipped: "no-subscribers" }. Not an error.

5. Send (see PART 2).

6. UPDATE sent_posts SET recipient_count = <actual> WHERE post_slug = $1

╔══════════════════════════════════════════════════════════════╗
║ PART 2 — SENDING                                             ║
╚══════════════════════════════════════════════════════════════╝

Use Resend's BATCH endpoint (resend.batch.send), not a loop of single sends.
Chunk into groups of 100.

Each email is PERSONALISED — every subscriber gets their own unsubscribe
token — so build one payload object per recipient.

  From:     Boost Web Digital <hello@boostwebdigital.com>
  Reply-To: ritik@boostwebdigital.com
  Subject:  the post title, verbatim, nothing prepended

Use the EXISTING renderEmail() from src/lib/email/template.ts. Do not build a
second template.

  preheader:  the post excerpt, trimmed to 100 chars
  heading:    the post title
  bodyHtml:   the excerpt as one or two paragraphs. STRIP ALL HTML TAGS from
              the WordPress excerpt first, then escape it. Never pass raw
              WordPress HTML into the email.
  bodyText:   the same text, unescaped
  cta:        { label: "Read the post", url: <the public post URL> }
  showSignature: true
  footerNote: You're receiving this because you confirmed your subscription
              at boostwebdigital.com. Unsubscribe: <unsubscribe URL>

The public post URL is https://boostwebdigital.com/blog/<slug>/ — the public
site, NEVER the blog.boostwebdigital.com CMS domain.

The unsubscribe URL is
https://boostwebdigital.com/newsletter/unsubscribe/?token=<their token>

─── REQUIRED HEADERS ───

Set these on every send:

  "List-Unsubscribe": "<https://boostwebdigital.com/api/newsletter/unsubscribe?token=TOKEN>"
  "List-Unsubscribe-Post": "List-Unsubscribe=One-Click"

Gmail and Yahoo expect bulk mail to carry these. Mail without them is more
likely to be filtered, and the recipient's only way out becomes the spam
button — which damages sender reputation far more than an unsubscribe does.

To support this, the POST /api/newsletter/unsubscribe route must ALSO accept
the token from the query string, not only the JSON body. Mail providers POST
to that URL with a form body, not JSON. Accept both. Return 200 either way.

─── RATE AND FAILURE HANDLING ───

- Resend free tier is 100 emails per DAY. If the confirmed-subscriber count
  exceeds 100, send the first 100, log a clear warning naming how many were
  skipped, and still return the real sent count. Do NOT silently truncate.
- A failure on one batch must not abort the remaining batches. Collect
  errors, continue, report the total actually sent.
- Wrap the whole send in try/catch. A total send failure must not throw out
  of notifySubscribers.

║ PART 4 — A WAY TO TEST WITHOUT SPAMMING REAL PEOPLE          ║
╚══════════════════════════════════════════════════════════════╝

the revalidate route.

  Body: { slug, email }

- Sends exactly ONE email, to the address given, using the identical
  rendering path as the real send.
- Does NOT touch sent_posts.
- Does NOT read the subscribers table.
- Returns 401 without a valid secret.

only way to test is to publish a real post to a real list.
